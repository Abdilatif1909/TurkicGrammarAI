# 5. Experimental Setup

## 5.1 Datasets

The experiments use the lexical, morphological, cognate, historical, and embedding resources stored in the project repository. The lexical layer covers eight Turkic language varieties: Uzbek (`uz`), Turkish (`tr`), Azerbaijani (`az`), Kazakh (`kk`), Kyrgyz (`ky`), Turkmen (`tk`), Uyghur (`ug`), and Old Turkic (`otk`). The canonical language-specific word files contain 100,030 records when the language manifest is excluded. These files are not used as a single unmodified training corpus. Instead, the embedding-dataset builder integrates selected lexical records with normalized files where available, lemma dictionaries, morphology benchmarks, cognate records, historical forms, and corpus hooks.

The cognate resources include 1,000 sets in the general cognate file and 2,000 sets in the cross-language cognate resource. The latter supplies the group identifiers and language-specific forms used by the cognate-aware embedding pipeline. In the final embedding dataset, 23,018 records are assigned to one of 2,000 unique cognate groups. Cognate membership is represented both as record metadata and as a training-corpus marker. These resources provide the repository-defined cross-language relations evaluated in the embedding, retrieval, and QA experiments; they are not presented as an independently expert-certified etymological gold standard.

The historical resource contains 2,000 historical-form records covering Azerbaijani, Kazakh, Kyrgyz, Old Turkic, Turkmen, Turkish, and Uzbek. Historical metadata includes available Proto Turkic, Old Turkic, Middle Turkic, and modern-language forms. After integration with cognate-derived lineage information, the embedding dataset contains 25,018 records with historical lineage and 215,162 individual lineage entries. These entries are used for training-context construction and historical retrieval. Repository validation reports identify generated or projection-based content and incomplete expert review as limitations; the historical benchmark therefore measures consistency with the project resources rather than external historical-linguistic validity.

The principal training resource is `backend/data/embeddings/embedding_dataset.jsonl`, which contains exactly 100,000 records. Its language distribution is 18,314 Uzbek, 15,798 Turkish, 10,372 Azerbaijani, 10,582 Kazakh, 10,499 Kyrgyz, 10,102 Turkmen, 13,916 Uyghur, and 10,417 Old Turkic records. The dataset contains 88,712 unique surface forms, 26,797 unique lemmas, and 26,798 unique roots; 75,429 records have at least one morphology feature. Each record stores a surface form, lemma, root, language code, feature list, cognate-group identifier, historical lineage, and source.

The source distribution comprises 70,170 records from the word datasets, 15,948 from cognate resources, 8,611 from lemma dictionaries, and 2,000 from historical forms. The remaining records originate from language-specific morphology benchmarks: 873 Uzbek lemma cases, 496 Azerbaijani cases, 495 Turkish cases, 307 Kazakh cases, 300 Old Turkic cases, 246 Turkmen cases, 246 Uyghur cases, 222 Kyrgyz cases, and 86 Uzbek derivational cases. Dataset construction uses a fixed source order, applies schema fallbacks for missing lemmas and roots, removes duplicate records using language, surface form, lemma, root, and source, and stops at the 100,000-record target.

## 5.2 Training Configuration

The embedding model is trained with Gensim FastText using the skip-gram objective. The line-oriented training corpus is generated from the JSONL dataset by placing lexical forms beside language, root, morphology, cognate, and lineage markers. Additional corpus lines group forms by cognate identifier, language-specific root, and morphology feature. This procedure exposes repository annotations as co-occurrence signals while retaining FastText character-level subword modeling.

Table 3 reports the complete stored training configuration. The vector dimensionality is 300, the context window is 5, the minimum count is 1, and training is performed for 20 epochs. The repository run used 12 workers and produced a vocabulary of 143,011 entries. The minimum count of one retains low-frequency words and specialized `COGNATE`, `LINEAGE`, `ROOT`, `LANG`, and `FEATURE` markers. The implementation does not override FastText character n-gram parameters; subword settings therefore follow the library defaults used by the installed project environment.

The corpus path recorded in Table 3 is `backend/data/embeddings/fasttext_corpus.txt`. The trained Gensim model is stored as `backend/models/turkic_fasttext.model`, and vectors are exported in word2vec text format as `backend/models/turkic_fasttext.vec`. The stored training record reports 172.217 seconds and a vocabulary size of 143,011. Exact processor, memory, accelerator, and operating-system specifications were not recorded. Accordingly, the experiments are described as having been conducted in the project environment; the observed time is retained as a repository measurement but is not used for hardware-normalized comparison.

## 5.3 Evaluation Benchmarks

Four repository benchmarks are used to examine the embedding and its downstream integration. The intrinsic embedding-quality benchmark contains 5,000 word pairs: 4,297 positive pairs and 703 negative pairs. Its category distribution is 1,790 cognate pairs, 702 cross-language equivalents, 553 morphological variants, 1,252 historical relations, and 703 negative pairs. Positive pairs are evaluated through cosine similarity and target ranking against sampled distractors. The observed embedding metrics are summarized in Table 4. Because the repository contains no separate baseline evaluation artifact, Table 4 marks baseline values and improvements as unavailable.

The semantic-search benchmark contains 2,000 queries. It comprises 350 exact-match queries, 550 cognate queries, 400 morphological queries, 350 historical queries, and 350 cross-language queries. Each case defines a query, one or more expected words, and a category. The evaluator requests up to 20 search results and records the rank of the first returned word appearing in the expected set.

The RAG retrieval benchmark contains 1,000 queries, divided equally among cognate, morphology, historical, and cross-language categories. For every query, the retriever returns up to 20 documents produced by its semantic and metadata-aware ranking procedure. Evaluation records the first rank at which an expected word occurs. The evaluator also stores per-query latency and source-contribution counts, although the present setup section does not use latency as a hardware-comparison measure.

The QA benchmark contains 1,000 questions, with 250 questions in each of four categories: cognate, historical, cross-language, and morphology. Every case provides the question, the intended query term, acceptable expected words, the expected source type, and the category. The QA evaluator requests ten answer items and ten supporting documents. It then compares returned words and source traces with the expected fields.

These benchmark files support deterministic engineering evaluation of the repository pipeline, but they are not independent external test sets. The semantic-search, RAG, and QA benchmark generators derive their cases from the same semantic index used during evaluation. The embedding benchmark is also assembled from repository cognate and embedding resources. Consequently, the reported measurements characterize internal retrieval consistency and regression behavior. They should not be interpreted as independent generalization estimates or as evidence of state-of-the-art performance.

## 5.4 Evaluation Metrics

Top-1, Top-5, and Top-10 are used for the positive pairs in the intrinsic embedding benchmark. For each positive pair, the first word is treated as the query and the second as the target. The target is ranked together with up to 50 randomly sampled distractors from a vocabulary subset containing up to 20,000 distinct surface forms. Top-\(k\) is the percentage of the 4,297 positive pairs for which the target appears at rank \(k\) or better. The evaluator uses a fixed random seed of 22 for benchmark construction and distractor sampling. Table 4 reports the stored Top-1, Top-5, and Top-10 values for the cognate-aware model.

Recall@1, Recall@5, and Recall@10 are used for semantic search and RAG retrieval. For a benchmark case, a hit occurs when at least one expected word appears within the first 1, 5, or 10 returned results. Recall@\(k\) is the number of hit queries divided by the total number of benchmark queries, expressed as a percentage. Since each case can contain multiple acceptable words, the metric tests retrieval of any listed expected item rather than one fixed target.

Mean reciprocal rank (MRR) evaluates the position of the first acceptable result. If the first expected word appears at rank \(r\), the reciprocal rank is \(1/r\); a query with no expected result receives zero. MRR is the arithmetic mean over all semantic-search or RAG benchmark cases. It therefore distinguishes early successful retrieval from hits that occur near the end of the evaluated result list.

Answer Accuracy is used for QA. A question is counted as correct when the set of returned answer-item words intersects the case’s expected-word set. Source Accuracy measures whether the expected source type occurs among the returned citations or the source traces attached to answer items. These definitions evaluate term-level answer support and source-type routing. They do not evaluate free-form linguistic explanation quality, because the repository QA component is a retrieval-based structured answer builder rather than a generative evaluator.

## 5.5 Experimental Procedure

The procedure begins by constructing the 100,000-record embedding dataset from the repository resources. Records are normalized into the common schema, enriched with available morphology, cognate, and lineage metadata, deduplicated, and written as JSONL. The corpus-preparation stage converts each record into a sequence of lexical and metadata tokens and appends grouped signal lines for cognates, roots, and features.

FastText vocabulary construction and skip-gram training are then performed using the configuration in Table 3. After training, the model and exported vectors are saved, and the semantic index is built from the same JSONL dataset. The index stores compact records and lookup maps for words, lemmas, roots, cognate groups, features, and lineage forms.

Evaluation proceeds from the embedding layer to downstream services. The embedding evaluator constructs or loads the 5,000-pair benchmark and computes cosine and ranking measures. The semantic-search evaluator generates 2,000 indexed retrieval cases and calculates Recall@1, Recall@5, Recall@10, and MRR. The RAG evaluator applies the metadata-enhanced retriever to 1,000 cases using the same rank-based measures. Finally, the QA evaluator sends 1,000 questions through query extraction, retrieval, and structured answer construction, then calculates answer and source accuracy.

Validation is based on stored statistics, evaluator scripts, manifests, and manuscript-facing traceability reports. Dataset and training values are direct counts or saved configuration values. Table 4 contains only observed cognate-aware metrics; unavailable baseline values are not estimated. The validation package also distinguishes direct measurements from derived analyses and documents benchmark leakage, candidate-gold status, provenance limitations, and the need for external expert review.

## 5.6 Reproducibility

The `paper_package` directory provides manuscript-facing reproducibility materials. Its `tables` subdirectory contains CSV, Markdown, and LaTeX versions of Tables 1–7, including the training configuration in Table 3 and embedding results in Table 4. The `figures` directory contains PNG and SVG versions of the paper figures. The `reports` directory summarizes extraction sources and package generation, while `analysis` stores statistical, ablation-proxy, and error-analysis notes.

The `paper_package/validation` directory contains table and figure validation, metric traceability, publication-evidence classification, result classification, threats to validity, reviewer questions, and paper-readiness reports. In particular, the metric traceability report maps dataset counts, training parameters, and evaluation values to their source files and evaluator scripts. The table validation report identifies Tables 1–3 as directly validated, while noting that Table 4 has no supported baseline comparison.

Additional reproducibility artifacts include the dataset and model manifests, the root-level reproducibility report, dependency files, embedding dataset, prepared corpus, saved FastText model, exported vectors, semantic index, benchmark JSON files, evaluator programs, and stored evaluation statistics. The reproducibility report documents backend, frontend, SQLite, PostgreSQL, and Docker setup paths and records successful project checks from the release-preparation phase. Reproduction of numerical results should use a fixed repository commit and preserve the benchmark-generation procedures and random seed. Exact hardware specifications cannot be reproduced because they were not recorded; therefore, runtime values should be treated as environment-specific observations rather than portable performance claims.
